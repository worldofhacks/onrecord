## Root cause

`_resolve_answer_fn()` (`onrecord/rag/qa_eval.py:392`) lazily does:

```python
import onrecord.rag.answer as _answer_module
```

The test fakes this out via `monkeypatch.setitem(sys.modules, "onrecord.rag.answer", fake_answer_module)`.

That works **only if `onrecord.rag.answer` has never been really imported in this process before**. `import a.b.c as x` is compiled by CPython as an `IMPORT_NAME` (which ensures `a.b.c` is loaded — a no-op if `sys.modules["a.b.c"]` is already present) **followed by an attribute walk from the top-level package** (`x = a.b.c`, i.e. `getattr(getattr(a, "b"), "c")`), not a direct `sys.modules["a.b.c"]` lookup. The parent-package attribute (`onrecord.rag.answer`) is only (re)bound by the module-loading machinery the first time `onrecord.rag.answer` is really imported; once bound, `monkeypatch.setitem(sys.modules, ...)` swaps the *registry* entry but never touches that already-set attribute.

`tests/unit/rag/test_answer.py` really imports `onrecord.rag.answer` (necessarily — it's the module under test), which permanently binds `onrecord.rag`'s `.answer` attribute to the real module for the rest of the process. `test_answer.py` sorts before `test_qa_eval.py` alphabetically, so in any run where both files execute in one process, by the time `test_resolve_answer_fn_real_composition_...` runs, `import onrecord.rag.answer as _answer_module` inside `_resolve_answer_fn()`'s real body resolves to the **real** `answer` module, not the test's `sys.modules`-injected fake.

Consequence: the real `answer()` runs instead of the fake. It receives `chunks=[]` (the test's fake `ranked_search` returns `[]`), which `answer()`'s own retrieval-confidence refusal path short-circuits **before calling `generate_fn`**, returning a refusal dict with no exception. So `_resolve_answer_fn()`'s closure returns normally, the fake `answer()` is never invoked, and `received_calls` stays empty — tripping the test's own "never invoked" assertion. The production wiring is not at fault: the same seam, exercised for real end-to-end against real disk artifacts (throwaway composition script, wave-9 integration verification), composes correctly with no arity/TypeError issue.

I confirmed this class of bug does **not** also lurk in T-026's parallel seam (`judge.py::_resolve_answers`, which also does `from onrecord.rag.answer import answer, default_generator` lazily) — exercised live with a tiny real corpus + fake transport, composed with no TypeError and the correct row shape.

## Fix direction (implementer's call, needs a test-design pass — this is a frozen-suite test, not throwaway)

Two independent candidate fixes; either is sufficient, they are not mutually exclusive:

1. **Test-side**: in addition to `monkeypatch.setitem(sys.modules, "onrecord.rag.answer", fake_answer_module)`, also `monkeypatch.setattr("onrecord.rag.answer", fake_answer_module)` via the `onrecord.rag` package object (i.e. `import onrecord.rag; monkeypatch.setattr(onrecord.rag, "answer", fake_answer_module)`) so both the registry and the parent-package attribute point at the fake — immune to prior-import order regardless of which other test files ran first. Lowest blast radius; keeps the seam's `import a.b.c as x` style untouched.
2. **Production-side**: change `_resolve_answer_fn`'s lazy import from `import onrecord.rag.answer as _answer_module` to `_answer_module = importlib.import_module("onrecord.rag.answer")`, which resolves via a direct `sys.modules` lookup (no parent-attribute walk) and is immune to this class of test-ordering gotcha by construction. Touches shipped code that already passed two review rounds — larger blast radius, needs re-review scrutiny if chosen.

Recommend (1) unless a reviewer prefers hardening the seam itself.
