## Context
The first full-corpus embed run failed: OpenAI /v1/embeddings returns HTTP 400 when any
input exceeds the model's per-input token cap (~8,192 for text-embedding-3-small).
Diagnosis against corpus/v2: 33 docs (all source_type=filing, longest 163,817 chars
~= 41K tokens) exceed ~32K chars; 0 empty texts. The 64-chunk smoke sample was
yt-only and never hit one. The store currently forwards raw text with no guard, and
EmbeddingRequestError names neither the batch nor the offending chunk.

ADJUDICATED DESIGN (orchestrator): deterministic TRUNCATION-FOR-EMBEDDING —
the vector for an over-limit text derives from its first EMBED_INPUT_MAX_CHARS
characters (module constant, 24000 — conservative ~6K tokens at 4 chars/token,
headroom for token-dense legal text). The store's entries/content_hash remain over
the FULL text (identity + staleness semantics unchanged — only the vector input is
bounded). Truncated chunk_ids are counted and logged (never silent). Sub-doc
splitting is OUT (would mint new chunk ids, colliding with the identity invariant).

## Acceptance Criteria
- **AC-1**: Given a (chunk_id, text) pair whose text exceeds EMBED_INPUT_MAX_CHARS, when
  embed_corpus runs, then the provider receives the first EMBED_INPUT_MAX_CHARS chars
  (byte-deterministic slice), the stored entry's content_hash is over the FULL text,
  and the store round-trips load() cleanly.
- **AC-2**: Given a mixed batch (normal + over-limit texts), when embed_corpus runs, then
  all rows are written, dedupe-by-hash still keys on the FULL-text hash, and a summary
  count of truncated chunk_ids is exposed (logged via the module logger AND returned or
  queryable — pin the mechanism the Test Agent judges most contract-true).
- **AC-3**: Given a provider HTTP 400, when _embed_batch raises EmbeddingRequestError, then
  the message names the batch index and the first offending chunk_id in the batch
  (error hygiene — operators must not have to bisect 289K chunks).
- **AC-4**: Existing 85-test suite untouched and green (additive-only).
