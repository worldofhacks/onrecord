## Context
Implements frozen `InvertedIndex` contract from T-001 (`onrecord/index/inverted.py`). Calls `onrecord.analysis.analyzer.analyze()` (T-002's scope — import it, don't reimplement; tests may use the real one). Postings per term: parallel arrays (`array('q')` or numpy) of doc ids (int internal ids, sorted), tfs, and per-doc position arrays (analyzer token indices). Keep an id↔doc_id map + doc store + doc lengths (needed later by BM25). Serialize via msgpack+npy to a directory.

## Acceptance Criteria
- **AC-1**: Given 3 docs where "substation" appears in 2 (3× in one, 1× in other), when built, then `df("substation")==2` and postings tfs are `[3,1]` with correct sorted doc ids.
- **AC-2**: Given a built index, when `postings(term).positions` are read, then they equal the analyzer's token indices for that term in each doc.
- **AC-3**: Given a built index, when `save(path)` then `load(path)`, then df/postings/doc store are identical (round-trip).
- **AC-4**: Given a built index, when `delete(doc_id)`, then the doc appears in NO posting list and `get_doc` raises KeyError; df values decrement where the doc was the sole/one holder.
- **AC-5**: Given a term absent from the corpus, when `postings`/`df` are called, then df==0 and empty postings — no exception.

## Test Plan
- Unit (deterministic): AC-1..5 on a small fixed fixture corpus of `Doc`s.
- Property (hypothesis): index random doc sets → every doc retrievable via each of its distinct terms (round-trip identity); delete then search never returns the doc; df equals number of docs containing term.

## Definition of Done
