## Context
T-024's review (I-1) flagged that `async def` handlers with synchronous bodies block
FastAPI's single event loop for the duration of that body — starving every other
in-flight request on the process, not just the caller's own. T-024 fixed this for the
endpoints in its own scope (`/api/search`, `/api/answer`) by converting them to plain
`def` (so Starlette dispatches them to the threadpool instead), and added the
`_EMBED_STORE_LOCK` machinery to make the now-genuinely-concurrent threadpool workers
safe against a cold-cache stampede (`onrecord/api.py`'s `_load_embed_store` docstring).

Two more endpoints carry the identical defect and were out of T-024's file scope (it
touches `onrecord/api.py` but its ticket was deliberately sized to the RAG unlock
only — README/deploy/UI/other-endpoint obligations were explicitly pushed to the
wave-10 integration checklist, not silently in-scoped):

- `GET /api/tickers` (`async def tickers()`) synchronously loops over every doc in the
  loaded index (`for i in range(index.doc_count())`) to build sector/ticker counts —
  CPU-bound work with no `await` inside it, blocking the loop for the full scan on
  every request (no caching, unlike `/api/stats`'s `_compute_stats` which is
  precomputed once at startup).
- `GET /api/prices/{ticker}` (`async def prices(...)`) calls
  `onrecord.ingest.prices.api_payload`, which — on a cache miss — makes a REAL
  synchronous network call (stooq, with an optional FMP fallback) directly inside the
  coroutine. This is the worse case of the two: a slow/hanging upstream price API
  stalls the entire process's event loop for the duration of that HTTP call, not just
  CPU time.

## Acceptance Criteria (sketch — Test Agent refines)
- AC-1: `tickers()` and `prices()` become plain `def` handlers (T-024's precedent,
  `onrecord/api.py` module docstring's "NOT `async`" convention already established on
  `search()`/`answer()`), so Starlette runs them in the threadpool instead of on the
  event loop.
- AC-2: a concurrency regression test (mirroring T-024's own event-loop-liveness
  pin) demonstrates the event loop stays responsive (e.g. `/health` answers promptly)
  while a slow `/api/tickers` or `/api/prices` request is in flight — red before the
  fix, green after.
- AC-3: existing `test_serve.py`/`test_api.py` coverage for both routes stays green
  unchanged (behavior/response shape is identical; only the dispatch mechanism
  changes).
- AC-4: no new thread-safety hazard introduced — `/api/tickers`' read-only index scan
  and `/api/prices`' cache-dir read/write should be checked against the same
  cold-cache-stampede class T-024's `_EMBED_STORE_LOCK` exists for; a lock is only
  needed if a genuine shared-mutable-state race is found (e.g. concurrent first-writes
  to the same price cache file).

## Out of Scope
Any other endpoint's dispatch mode (`/health`, `/api/metrics`, `/api/stats`, static UI
serving) — none of them do blocking work in their bodies today, so they are not this
defect class. Rate limiting or timeouts on the upstream price provider itself.
